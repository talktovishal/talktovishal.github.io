Learning by doing

Tokenization: How text is converted into tokens that a model can read.

I type unbelievable, and it feels like one word to me. To the model, it might be one piece, three pieces, or a handful of raw bytes. That choice influences cost, speed, context length, and even some of the strange mistakes people blame on LLMs. Hence, it's important to understand how tokenization works. In this chapter, we'll understand the details of tokenization by building a simple tokenizer from scratch and exploring all its nuances.

A neural model never sees your letters directly. Not one. It sees token IDs - plain integers that map into its embedding table - and nothing else. Before any LLM math can happen, a separate program called the tokenizer chops your text into known pieces and looks up their numbers. Each number represents a specific subword or token that the model has learned to recognize. For example, the word "unbelievable" might be tokenized into three tokens: "un", "believ", and "able". Remember, in Chapter 2, we learnt how a particular word gets mapped to a list of numbers aka vector. We now learn this process in detail and see modern LLMs, first break down the text into subword pieces and then use their vectors during their processing.

Guiding question: if the word supercalifragilisticexpialidocious :-) never appeared in training, how can the model still handle it? The answer is not that the model owns a giant dictionary of all possible words. It is that the word was stored as smaller parts, each of which the model has seen many times.

  • Chapter 1. We reuse the idea of a vocabulary and the fact that every model reads token IDs (integers), never letters.

What you do not need: any of the gradient or softmax math - that arrives right after this, in Chapter 4. A tokenizer does not learn by backprop - it just counts, merges, and looks things up.

1. Why tokenization matters

The same sentence can be cheap or expensive, depending on the pieces.

Chapter 1 used the friendliest possible tokenizer: split the text on spaces, then count the words. That was exactly right for our first model, but it hid a real decision. Should the unit be a whole word, a single character, a raw byte, or a subword chunk in between? Each answer changes how many tokens the same sentence becomes, and token count is what you pay for in money, memory, and latency.

The picture I keep in my head is cutting the same sentence into different sized building blocks. Whole words are easy to read, but rare words have no entry and break. Characters and bytes can spell anything, but they make long sequences that are slow and expensive. Subwords are the middle path used by almost every modern model: keep frequent pieces whole, split rarer words into reusable parts. Type into the box and watch the four views disagree on the very same text.

I am going to break my rule and talk about Transformers - the main architecture used in modern LLMs. It's important to understand the impact of tokenization on the performance of these models. More tokens mean more steps for the model to process, more memory to hold them, and more token-to-token comparisons when the full prompt is read. If a prompt has T tokens, that comparison table has about T * T cells. Double the token count and the table becomes roughly four times larger. You do not need the machinery behind that fact yet; the worked example below is the part I want you to feel.

Optional: why Transformer cost grows faster

During attention, each token's current representation is projected into queries, keys, and values. The attention layer compares tokens with query/key dot products, then uses those scores to mix value vectors from the surrounding tokens. That is where the T * T table comes from during full-context attention and prompt prefill.

During autoregressive generation, a KV cache changes the per-token cost because earlier keys and values can be reused, but a long prompt still pays its token budget up front. The tokenizer also helps choose the size of the embedding table: with V vocabulary pieces and d numbers per vector, that table has V * d learned numbers. A larger vocabulary can shorten sequences, but it also creates more rows for the model to learn. Do not worry if some of this is still fuzzy - we will go into it in detail in the subsequent chapters.

Token cost by hand

Imagine one sentence becomes 12 tokens with a good subword tokenizer, but 20 tokens with a byte-heavy tokenizer. The text looks the same to you, but while reading the full prompt, the Transformer has more token-to-token pairs to score.

attention cells with 12 tokens = 12 * 12 = 144 attention cells with 20 tokens = 20 * 20 = 400 400 / 144 = 2.8x as many token-to-token scores

This is why a word that splits into many pieces has a real token tax: it can cost more memory, more time, and more money even before the model starts reasoning about meaning.

2. Down to the bytes

The simplest tokenization strategy - breaking text all the way down to bytes.

The opening section let four rules - word, character, byte, subword - argue over the same sentence. But it skipped a fair question: what is a "piece" made of? When I first learned this, it felt almost too low-level, like we had left language behind. Hence, it is the right place to start. To a computer, a string is a sequence of Unicode code points. Unicode is a giant catalogue - about 150,000+ characters across 161 scripts, and still growing every single year - that hands one integer to every character humanity writes, from A to あ to 👍. The letter H is code point 72; that thumbs-up is 128,077.

So why not feed the model those code-point integers directly and call it a day? Two reasons, and both bite. First, the vocabulary would be enormous - 150,000 rows in the embedding table before the model has learned anything. Second, and worse, Unicode is a living standard: new characters land every year, so today's numbering is a moving target. We want a base that is smaller, fixed, and universal.

That base is UTF-8, the encoding nearly all of the internet already speaks. UTF-8 takes each code point and writes it out as 1 to 4 bytes - and a byte is simply a number from 0 to 255. Plain English letters take 1 byte each (UTF-8 is backward-compatible with old ASCII); accented letters and most scripts take 2 or 3; an emoji takes 4. So here is the bedrock fact for the whole chapter: underneath the text itself, any text at all - English, Korean, source code, emoji - is just a stream of bytes, each between 0 and 255. A byte-level base needs a vocabulary of exactly 256, it can spell literally anything ever written, and nothing can crash it with a character it has never seen.

There is one catch, and it is the entire reason the next section exists. If we stop at raw bytes, sequences get long - that emoji alone is four tokens, an everyday English word is several - and a Transformer can only attend to so many tokens at once. Raw bytes squander that budget. So GPT-style byte-level tokenizers keep the universal 256-byte foundation and build on top of it: glue the byte pairs that show up most often into new, longer tokens. That gluing algorithm is called byte-pair encoding (BPE).

One string, all the way down to bytes

Take the four-character string Hi 👍 - an H, an i, a space, and a thumbs-up. Python's ord() gives each character its Unicode code point; UTF-8 then rewrites each code point as bytes:

code points: H = 72 i = 105 space = 32 👍 = 128077 UTF-8 bytes: [72] [105] [32] [240, 159, 145, 141] 4 characters → 7 bytes, because the emoji alone needs 4 bytes

This is important. The model never sees an "emoji" - it sees the four bytes 240 159 145 141. Almost every quirk later in this chapter - shaky spelling, broken arithmetic, expensive Korean - begins right here, with how these bytes get grouped into tokens.

3. Complete tokenizer systems

Four paths from raw text to tokens.

Let's slow down and get this right. If tokenization feels fuzzy, your understanding of how an LLM actually works will stay fuzzy, too. To reiterate: a tokenizer is a separate object from the language model. It has its own training corpus, learns a vocabulary once, assigns integer IDs to those pieces, and then freezes. The giant neural model only ever sees the integer IDs the tokenizer produces. It cannot renegotiate the pieces later.

This makes the tokenizer's choices critical: they decide how many tokens a sentence costs, how much of your context window is consumed, and whether a rare word survives intact or shatters into fragments. Its job is essentially a budget decision: which chunks of text deserve their own row in the vocabulary? Make the chunks too big, and the vocabulary explodes. Make them too small, and every sentence becomes a long, expensive chain. Subword tokenization was invented to live in the middle.

First, "word" is not a clean unit.

Is pool, one word, or a word plus a comma? Is I'm one word, or I plus 'm? Chinese, Japanese, and Thai do not always mark word boundaries with spaces, and words like longer contain meaningful pieces such as long and -er. So a tokenizer is never merely "splitting on spaces"; it is actively choosing a boundary policy before the model sees anything.

We already felt the word-versus-byte tradeoff earlier. Now we can focus on the part that usually causes confusion: how four real tokenizer systems prepare text, learn pieces, and split new text in different ways.

First, separate the method from the software around it.

Let's keep the names simple. BPE, WordPiece, and Unigram are three different methods for learning and using subword pieces. SentencePiece is software that can build a complete tokenizer using either the BPE method or the Unigram method. SentencePiece does not offer WordPiece as one of its methods. So SentencePiece BPE simply means: SentencePiece handles the raw text, spaces, and other setup, while BPE learns the pieces. A BERT WordPiece tokenizer follows a completely different path.

Whichever complete system we choose, a finished tokenizer must answer the same four questions: How is the input prepared? What small pieces can it start or fall back to? How does it learn larger pieces? How does it split and rebuild text when we use it? We will ask those questions of each system in exactly that order.

One sentence, four complete paths.

We will carry playing cats! through every system. To make the final cuts concrete, imagine each tokenizer has already trained on a corpus where pieces such as play, ing, cat, and s were highly useful. Real pieces depend on the training corpus; the path each system follows is the lesson here.

1. GPT-style byte BPE

A GPT-style tokenizer first uses a set of rules (regular expressions) to carve the text into isolated regions that BPE is not allowed to cross. For our example, a simplified view is playing | ␣cats | !, where ␣ makes the leading space visible in our notation; it is not a special tokenizer character like SentencePiece's ▁. Each region is then converted to UTF-8 bytes. Because all 256 byte values are available from the start, any Unicode text can be represented without missing characters.

During tokenizer training, BPE repeatedly merges the most frequent adjacent pair and records the ordered merge rules. When new text arrives, the encoder starts from bytes and applies those learned rules in exact order. The final pieces map back to bytes, which decode to the original text.

Input preparation: playing cats! -> playing | ␣cats | ! -> UTF-8 bytes Base and coverage: all 256 byte values; no unknown characters Learning: BPE repeatedly merges the most frequent adjacent pair and records the ordered merge rules Use: start from the base pieces and apply the learned BPE merge rules in order -> play | ing | ␣cat | s | ! -> decode bytes

2. SentencePiece BPE

SentencePiece does not require a separate word splitter. It natively ingests raw text, applies its configured cleanup (normalization), and makes spaces visible as ▁. Our example becomes ▁playing▁cats!. Its base vocabulary contains required Unicode characters; an optional byte fallback can be turned on to cover any character not in that base.

From there, this uses the same BPE method as the first path: it learns frequent adjacent-pair merges, records their order, and applies those rules to new text. Only the preparation around BPE has changed. Decoding simply joins the pieces and turns ▁ back into standard spaces, reconstructing the normalized input.

Input preparation: playing cats! -> ▁playing▁cats! Base and coverage: required Unicode characters; optional byte fallback Learning: BPE repeatedly merges the most frequent adjacent pair and records the ordered merge rules Use: start from the base pieces and apply the learned BPE merge rules in order -> ▁play | ing | ▁cat | s | ! -> decode normalized text

3. BERT WordPiece

BERT first runs a BasicTokenizer: it cleans the text, applies the model's case and accent choices, separates punctuation, and creates spans. Our example becomes playing | cats | !. These spans act like fences, not guaranteed linguistic words. WordPiece may split words inside a fence, but it will never combine letters across two different spans.

In the standard teaching reconstruction, training starts a span such as playing as p ##l ##a ##y ##i ##n ##g and favors pairs with a strong association score. At runtime, it does not replay merge rules. Instead, it searches the final vocabulary from left to right and takes the longest valid piece at each position. If a complete path cannot be found, the entire span collapses into an unknown [UNK] token.

Input preparation: playing cats! -> playing | cats | ! Base and coverage: first characters + ##continuations; [UNK] if a span has no complete path Learning: build a final vocabulary of start and continuation pieces Use: greedy longest-match inside each span -> play | ##ing | cat | ##s | !

The same BasicTokenizer treats scripts differently without running a full language-specific word breaker: 我喜欢猫。 becomes 我 | 喜 | 欢 | 猫 | 。, while unspaced Thai such as ฉันชอบแมว is usually one long span whose success depends entirely on the learned vocabulary. Google released BERT's runtime tokenizer, but not its original trainer; the association-score rule used later in this chapter is the standard teaching reconstruction.

4. SentencePiece Unigram

This path begins with the exact same SentencePiece preparation as SentencePiece BPE: normalize the raw sentence and represent spaces with ▁. The difference begins at learning time. Unigram starts with a massive set of possible pieces, estimates a probability for each one, and prunes away the pieces that contribute the least value until it hits its target vocabulary size.

At runtime, all pieces that could theoretically cover the text form a web of possible routes. The encoder uses dynamic programming to choose the route with the lowest total "surprise" (the highest overall mathematical probability). It does not replay a BPE merge list, and it does not use WordPiece's greedy longest-match rule.

Input preparation: playing cats! -> ▁playing▁cats! Base and coverage: a large seed set of characters and substrings; optional byte fallback Learning: estimate piece probabilities and prune pieces that add the least value Use: choose the lowest-surprise complete route -> ▁playing | ▁cat | s | ! -> decode normalized text

That is the whole family. GPT-style byte BPE and SentencePiece BPE share the BPE algorithm but wrap it in different preparation and coverage choices. WordPiece uses a final vocabulary plus longest-match. SentencePiece Unigram uses scored alternatives plus a lowest-surprise route. Before the final side-by-side summary, the two optional notes trace where these systems came from and how current model families choose between them.

Optional history: how these branches emerged

Let's see how these systems came to be. Byte-pair encoding began back in 1994 as a data-compression trick: repeatedly fuse the most common adjacent byte pair into a new symbol. Two decades later, Sennrich and colleagues reused that merge idea for machine translation, where a fixed vocabulary keeps meeting rare names and compounds. Splitting them into reusable subword pieces beats dropping them into an unknown bucket. Google's GNMT answered the same need with WordPiece, which favors pieces that are distinctively paired rather than merely frequent, though it, like BERT after it, still segmented within boundaries prepared before the subword algorithm ran. In 2018, SentencePiece made that external word-boundary stage unnecessary: it trains directly from sentences after its own configurable normalization, with spaces kept as the visible marker ▁. Space-free languages and mixed scripts can therefore share one tokenizer without needing separate word segmentation software.

Now let's see why LLMs like GPT-2 started to leverage BPE. An open-ended web model has to give some probability to any Unicode string, so it used byte-level BPE: bytes guarantee coverage, BPE adds compression. BERT's WordPiece fit a different job (distinctive subwords for masked-token understanding), and SentencePiece fit yet another (raw multilingual text with spaces represented in the model itself).

This split is still how it works today. DeepSeek-V3 and Qwen2.5 both use byte-level BPE with large (128K–150K) vocabularies, while Baichuan 2 runs BPE inside SentencePiece with UTF-8 byte fallback. One more reminder that "SentencePiece BPE" is not a competitor to BPE, just BPE trained inside SentencePiece's raw-text machinery.

Optional: how current model families make the tradeoff

Two broad packaging styles appear often in modern LLMs, so it is worth asking how model builders choose between GPT-style byte-level BPE (OpenAI's tiktoken, encodings like cl100k_base and o200k_base) and a SentencePiece-based tokenizer. The honest answer is a tug-of-war between multilingual purity and strict structural control for math and code. But that is not the only axis: boundary policy, Unicode coverage, vocabulary size, compression on the actual training languages, and runtime packaging all pull on the decision. Following are the considerations:

1. Regex pre-splitting buys structural control. SentencePiece can train directly on raw text, without an external language-specific word splitter. In its BPE mode, it can therefore fuse whatever neighboring pieces are frequent and allowed by its learned representation: perhaps a comma near a word (, The), or a whole year such as 1999 or 2024. GPT-style tokenizers often run a strict regex first (the pre-tokenization step we dissect in the next section), so BPE learns only inside the regions that regex creates. In particular, OpenAI's cl100k_base and o200k_base definitions keep letters, punctuation, whitespace, and digits in deliberately shaped regions and group digits into one-to-three-digit runs. That consistency can be useful for math and code, where steady number and whitespace boundaries give the model more regular building blocks than a chaotic mix of lone digits and giant clumps. The one-to-three-digit rule is a documented property of those named encodings, not a rule every byte-level tokenizer must follow.

2. Bytes guarantee zero unknown characters. A character-based SentencePiece model without byte fallback starts from the Unicode characters covered during training, so a rare emoji or an unfamiliar script can fall through to an <unk> token and the model loses the original character. Modern SentencePiece can switch on byte fallback, so this is not an unavoidable SentencePiece weakness; it is a choice in the tokenizer configuration. GPT-style byte-level BPE converts everything to UTF-8 bytes first, with a base of exactly 256 byte values. So, as we saw down in the bytes section, every Unicode string has a byte representation and cannot hit an out-of-vocabulary character. This is why we have to compare complete tokenizer systems, not toolkit names alone.

3. Raw text stays multilingual and self-contained. The same hand-designed regex that gives structural control is also a policy: its rules about spaces, punctuation, contractions, and digits can fit some languages and domains better than others. SentencePiece learns directly from raw sentences, treats whitespace as part of its representation, and does not require a language-specific word splitter. That made it a natural fit for systems such as T5 and the early Gemma tokenizers, and it remains attractive when many scripts and word-building systems have to share one vocabulary. It also commonly ships as a self-contained .model file, so an inference server can reproduce the exact normalization, vocabulary, and segmentation rules without separately re-matching an application regex.

So which wins? For years SentencePiece was the open-source default: Llama 1 and 2 and T5 shipped SentencePiece-based systems, and Mistral documents Tokenizers V1, V2, and V3 as SentencePiece-based. Llama 3 then adopted a tiktoken-derived vocabulary: Meta's Llama 3 report documents 128K pieces—100K from the tiktoken3 tokenizer plus 28K added to better support non-English languages—and reports that its English sample improved from 3.17 to 3.94 characters per token compared with Llama 2. Mistral's naming needs extra care: Tokenizer V3 remains SentencePiece, while V3-Tekken is the tiktoken-based branch. Those sources document what shipped, the vocabulary sizes, and the measured compression. They do not say that one coding benchmark single-handedly caused the changes. The broader lesson is not that one family is simply better; it is that the tokenizer follows the job. SentencePiece is attractive when raw multilingual coverage and self-contained packaging lead. A regex-plus-byte design is attractive when explicit boundaries, complete byte coverage, and structural regularity lead. The actual winner still has to be measured on the languages and data the model will read.

4. Build the learning rules

One corpus. Three rules. One decision at a time.

Section 3 compared complete tokenizer systems: preparation, coverage, learning, and runtime encoding. Here we hold the preparation still so you can feel the one decision that changes. BPE rewards raw pair frequency. WordPiece rewards distinctive association. Unigram LM prices complete routes and prunes pieces that add little value.

Optional: how GPT-style regex boundaries prepare text for BPE

If we run BPE completely naively, it wastes vocabulary slots on near-duplicates like dog, dog., dog!, and dog?. Hence, GPT-2 first splits text with a regular expression: contractions, Unicode letters, Unicode numbers, punctuation, and whitespace become separate regions, and BPE only merges within a region. OpenAI's newer cl100k_base and o200k_base definitions keep the same split-then-merge idea and tune a few places:

  • Digits are grouped in one-to-three-digit runs. In these encodings, 1234567 is pre-split as 123, 456, 7 before vocabulary merges are replayed.
  • Whitespace gets explicit grouping rules. These regexes can keep useful runs together instead of treating every indentation space as an unrelated region.
  • Contractions get case-aware rules. DON'T and don't are less likely to split in oddly different ways.
Regex bucket Example chunk Why it matters before BPE
Contractions We're → We + 're Common endings like 's, 're, and 't can be handled consistently.

Tiny caveat for later: some newer research tokenizers add a second stage that can merge across spaces or punctuation after the safer first pass. The learner idea is still the same: the boundary policy decides what the learning rule is allowed to consider.

Act 1: BPE builds upward from frequent neighbors

In the GPT-style byte story, each plain ASCII letter below is exactly one byte, so we write the byte as its readable letter (If we had emojis or accented characters, they would first shatter into multiple raw bytes). BPE asks one question during training: which adjacent pair appears most often? Runtime later replays the frozen merge list; it never recounts the new prompt.

Act 2: WordPiece rewards distinctive neighbors

WordPiece starts each prepared span with a bare first character and marks all subsequent characters with ## (meaning "this attaches to what came before"). This helps the model distinguish between an s at the start of a word (like sun) and an ##s at the end of a word (like hugs). It then asks not merely "which pair is common?" but which pair occurs together more specifically than its separate piece counts would suggest?

Score(A, B) = count(AB) / (count(A) * count(B)) Score(##u, ##g) = 20 / (36 * 20) = 1/36 Score(##g, ##s) = 5 / (20 * 5) = 1/20 1/20 > 1/36, so WordPiece first adds ##g + ##s -> ##gs
Held fixed: the weighted corpus and target word hugs Training evidence: position-aware pair and piece counts Training decision: add the largest association score Runtime rule: greedy longest-match over the final vocabulary

Stop training after that one addition. BPE starts from h u g s and applies its learned priority u+g -> ug, producing h | ug | s. WordPiece does not replay the training merge. It searches the final vocabulary from left to right: take start piece h, then continuation ##u, then the longest available continuation ##gs. Its result is h | ##u | ##gs.

Building differs: raw pair count versus association score. Breaking new text differs too: ordered BPE merge priorities versus WordPiece longest-match over a final vocabulary.

Imagine you only have a strict budget of 30,000 "slots" to store the most useful chunks of language. BPE fills those slots by acting like a pure data-compression tool: in our exercise, it simply counts which letters or chunks sit next to each other most often (like t and h) and merges the most frequent pair to save space. It does not ask whether the combination carries clean linguistic meaning; for this rule, raw frequency wins.

WordPiece, on the other hand, acts more like a linguist trying to make every vocabulary slot carry a useful, distinctive piece of language. The analogy is not entirely fanciful. In a BERT-style pipeline, a pre-tokenizer first draws boundaries using whitespace and punctuation, with extra language- or script-aware handling where needed; WordPiece then searches for reusable pieces within those boundaries. Google notes that subword units often retain linguistic meaning, such as morphemes. But WordPiece itself is not reading a dictionary or understanding meaning the way a human linguist does. The original method chose vocabulary additions based on how much they improved the likelihood of the training text.

Our simplified teaching rule below gives us an intuitive way to see that statistical preference. Imagine WordPiece choosing between th and qu in an ordinary English corpus. A raw-frequency rule may be drawn to th because t and h are both common and appear together frequently. WordPiece's score discounts a pair when its individual pieces are already common everywhere else. By contrast, because q appears far less often without u, the pair qu can receive a stronger distinctive-association score: their appearance together is harder to explain simply from the separate frequencies of q and u. The exact result will always depend on the corpus—WordPiece does not automatically declare th statistical noise or always merge qu—but the example captures the pressure created by its scoring rule.

That is why WordPiece is not merely "BPE with a different tie-breaker." It tries to avoid spending a precious vocabulary slot on a pair whose high count comes mainly from two ingredients that are already common everywhere. This statistical pressure can produce stable, reusable pieces that line up with stems, endings, and other meaningful patterns—pieces such as play and ##ing when the learned vocabulary supports them—although that linguistic alignment is an outcome, not a guarantee. Such pieces are useful for BERT-style masked-token prediction because the model can work with recurring parts of words rather than only isolated letters or memorized whole words. The picture I keep in my head is this: a linguist sets the workspace, a statistician chooses the pieces, and the resulting vocabulary can look as though the two collaborated.

The score used in this lesson, count(AB) / (count(A) * count(B)), is our simplified teaching rule for making that association visible. Production WordPiece training descriptions and implementations are not all identical, so keep the comparison at the right level: BPE rewards raw pair frequency here; our WordPiece exercise rewards a pair that occurs together more specifically.

Act 3: Unigram prices complete routes

Do not picture another greedy merge. Picture a menu of candidate pieces. During training, Unigram learns one probability for every surviving piece. Then, at encoding time, it uses those probabilities to choose a complete route through new text. Let us first follow how training creates that probability table, then freeze it and use it.

How training learns the probability table

Training starts with an oversized candidate vocabulary: every required character plus many frequent substrings such as hu, ug, and hug. The core dilemma is a chicken-and-egg problem: to know a piece's probability, we need to know how often it is used. But to know how often it is used, we first need to decide how to split the words!

The Expectation-Maximization (EM) algorithm solves this by alternating between guessing and updating. In the Expectation step (E-step), the model uses its current baseline probabilities to score every valid way to split a word. It scores a route by multiplying the probabilities of its individual pieces.

An E-step example with numbers

Imagine our toy model currently guesses P(hug) = 0.20 and P(s) = 0.08. The score for the route [hug][s] is 0.20 × 0.08 = 0.016.

Instead of picking just one winner, the E-step shares the credit proportionally. Suppose we calculate the scores for all five possible ways to split the word hugs, and those scores add up to 0.0288736. The route [hug][s] accounts for about 55.4% of that total (0.016 / 0.0288736 ≈ 0.554).

If the word hugs appears 5 times in our training document, this route claims 55.4% of those occurrences. Therefore, it adds 5 × 0.554 ≈ 2.77 estimated uses to the running tally for the piece hug, and about 2.77 uses to the tally for s. The remaining 44.6% of the credit is distributed to the pieces in the other routes (like h, ug, etc.).

In the Maximization step (M-step), the model takes those accumulated estimated counts and updates its beliefs. It divides each piece's total estimated count by the grand total of all pieces. For instance, if hug gathered 10.75 total uses across the whole document, and the sum of all pieces everywhere was 100, the new P(hug) becomes 0.1075. Pieces that consistently help form high-scoring routes see their probabilities rise, while unhelpful pieces drop.

The trainer repeats this E-step/M-step loop until the probabilities stop shifting. Then, it tests the waters: how much would the corpus loss (total surprise) rise if each non-essential piece disappeared? It prunes away a batch of the least helpful pieces (always keeping required single characters so no text becomes un-encodable) and runs EM again. This prune-and-train cycle repeats until the vocabulary shrinks to the target size.

initialize: large candidate vocabulary + initial probabilities E-step: current probabilities score every valid route to share estimated counts M-step: P(piece) = estimated count(piece) / total estimated count prune the least harmful pieces, rerun EM, stop at the target vocabulary size

From one learned probability to one piece cost

Why do we calculate cost with -ln P(piece)? Multiplying many small probabilities together (like 0.20 × 0.08) creates tiny decimals that computers struggle to handle accurately. Taking the negative natural logarithm (-ln) safely converts these multiplying probabilities into positive, additive "costs". A high probability piece gets a low cost, while a rare piece carries a high cost (high surprise).

Our walkthrough starts after training with a small, illustrative probability table. Suppose the frozen model has learned P(hug) = 0.20 and P(s) = 0.08. In the first step below, other pieces = 0.08 total simply groups the rest of the toy vocabulary so the probabilities add to 1.

cost(piece) = -ln P(piece) cost(hug) = -ln(0.20) ≈ 1.61 cost(s) = -ln(0.08) ≈ 2.53 cost([hug][s]) = 1.61 + 2.53 ≈ 4.14
illustrative routes for hugs: [h][u][g][s], [hu][g][s], [h][ug][s], [hug][s], [hugs] route cost = -ln P(piece1) - ln P(piece2) - ... training output: one learned probability for every surviving piece encoding: choose the lowest-surprise complete route
Held fixed: the weighted corpus and target word hugs Frozen model: one learned probability per candidate piece Training decision: keep useful pieces and prune weak ones Runtime rule: choose the lowest-surprise route

Optional: how dynamic programming avoids brute force

A long word can have many possible cuts. Dynamic programming walks from left to right and stores only the cheapest known way to reach each character boundary. When a more expensive route reaches the same boundary, the encoder can discard it immediately because both routes face the same remaining suffix.

best cost at h = min([h]) = 2.12 best cost at hug = min([h][u][g], [hu][g], [h][ug], [hug]) = 1.61 best cost at hugs = min(1.61 + 2.53, 4.61) = min(4.14, 4.61) = 4.14

The answer is still the same route you calculated above: [hug][s]. Dynamic programming changes the amount of search, not the scoring rule or the winner.

The dynamic programming part is just the efficient way to avoid trying every possible cut by brute force. The learner intuition is simpler: SentencePiece (Unigram LM) keeps a scored menu of plausible pieces, then finds the lowest-surprise path through the word or sentence. Its big practical win is not "newer than WordPiece"; it is raw-text, language-independent tokenization with spaces preserved in its normalized representation.

About the lab below: this is a teaching toy for the learning rules, not a clone of GPT-4, BERT, or SentencePiece. Each algorithm really runs: BPE merges by raw frequency, WordPiece merges by the count(AB) / (count(A) × count(B)) score, and Unigram LM starts from a big candidate set and prunes low-probability pieces. To compare the learning rules fairly, the first three choices all use the same lowercase word/punctuation spans and character base. The lab therefore skips production regex chunks, raw SentencePiece spaces, byte fallback, normalization, and special tokens. Its Unigram trainer also uses only each word's single best Viterbi route as a faster hard approximation; full EM shares credit across every plausible route as described above. 5. Why models break: the tokenization quirks

Many "the model is dumb" moments are really tokenizer moments.

A startling number of an LLM's famous failures begin with, or are amplified by, tokenization. That does not absolve the neural network, its training data, or the rest of the system. It tells us where to inspect first. Remember the bedrock fact: the model receives token chunks, not a separate input slot for every visible letter. Tasks that need boundaries hidden inside a chunk can therefore be harder, and text that becomes many chunks is more expensive.

Pick a case in the lab below and watch the token stream; sometimes the visible text and the tokenized input are far less alike than they look. But first, let's make a little field guide. Each quirk below has been observed in a named tokenizer or model family. Token boundaries help explain the behavior, but they are one part of the larger model and training system.

A token tax is evidence, not destiny

Suppose two names are equally important in the real world, but the tokenizer learned one from many examples and barely saw the other. The common name might be one token while the rare name becomes five pieces. That difference does not prove unfair behavior by itself, but it is a signal worth inspecting.

cost(common name) = 1 token cost(rare name) = 5 tokens same sentence + rare name = 4 extra tokens of context budget

This is the quiet fairness lesson in tokenization: representation begins before the neural network. A model can only learn from the pieces its tokenizer gives it. If the tokenizer's training corpus is dominated by one language or domain, that language often gets cheaper, chunkier pieces, while other languages pay more tokens for the same amount of meaning.

Spelling can become harder A tokenizer may package a word such as DefaultStyle into one or a few opaque chunks. Letter-level tasks then depend on the model reconstructing boundaries it was not given directly.
Shaky arithmetic Number boundaries depend on the encoding. OpenAI's cl100k_base and o200k_base pre-tokenizers group digits in one-to-three-digit runs; other tokenizers make different choices.
Non-English can cost more An English-dominated vocabulary may keep common English words whole while splitting basic Spanish, Hindi, Korean, or Thai words into many pieces. More pieces means more context budget and training compute for the same message.
Old tokenizers taxed Python Some older GPT-style encodings represented indentation inefficiently, making code consume more context. Newer encodings can group whitespace more deliberately.
Trailing whitespace can cause hiccups Many GPT-style tokens fold a leading space into the word that follows it. A lone trailing space at the end of your prompt can force the tokenizer to use a rare, fragmented boundary for the next word, disrupting the pattern the model expects to see.
Special tokens need care Reserved strings such as <|endoftext|> can carry control meaning when an application allows them to be encoded as special tokens. Robust tokenization APIs often reject or escape them by default.
SolidGoldMagikarp and Glitch Tokens The famous Reddit username became an under-trained “glitch token”. It existed in the tokenizer's vocabulary (which was scraped from a massive dataset) but was virtually absent during the neural network's actual training. When asked to process this token, models produced bizarre, hallucinated outputs.
YAML can be shorter than JSON Because JSON relies heavily on repeating braces and double quotes, it can fracture into more tokens. For some data structures, YAML uses fewer pieces. It is not a universal rule; choose “JSON versus YAML” in the lab and compare this toy tokenizer's actual counts.
