Learning by doing

Making attention fast: the tricks that let it scale.

The attention you built in Chapter 5 is correct but expensive. This chapter is about every clever thing engineers do to keep it affordable, and what each trick costs you in return.

Here is the thing that surprised me most when I started reading modern architecture papers. The attention mechanism itself has barely changed since 2017. Query dot key, divide by the square root, softmax, blend the values. That is still what a 2026 trillion-parameter model does. Almost everything that has changed is about one question: how do we run that same math on longer inputs, on more tokens per second, without melting the GPU?

So this is not a chapter of new mechanisms so much as a chapter of pressures. Each section names a pressure, shows you the arithmetic that creates it, and then shows the trick the field invented to relieve it. When you finish, the boxes in an architecture diagram - GQA, MLA, SwiGLU, sliding window, MoE - should stop looking like a wall of acronyms and start looking like a list of answers.

Guiding question to keep in your pocket: in Chapter 5 you attended over six tokens. What actually breaks when that becomes a hundred thousand tokens, and which part of the machine breaks first?

Before we dive in, a few prerequisites are in order. This chapter leans hard on the machinery from Chapter 5, so make sure those parts feel solid. Use the links as quick refreshers.

  • Query, key, value. Every token produces three vectors, and attention is a query scoring against keys and blending values.
  • The attention matrix and the causal mask. Every token attends to every earlier token, which is what makes the cost grow the way it does.
  • Multi-head attention. Several heads run in parallel, each with its own queries, keys, and values.
  • The autoregressive loop. Generation is one forward pass per token, with the prompt growing each time.

What you do not need yet: how any of this was trained. We treat the model as finished and ask only what it costs to run. Training, data, and alignment are Chapter 7.

1. The two costs

Two different things get expensive, and people mix them up.

Let's be precise, because "attention is expensive" gets used for two problems that have completely different fixes.

Cost one: the pair count. In one forward pass over a sequence of \(n\) tokens, every token computes a score against every token it is allowed to see. That is roughly \(n^2/2\) scores once the causal mask removes the future. Double the context and you quadruple the scoring work. This is the famous "attention is quadratic" complaint, and it applies to reading a long prompt.

Cost two: repeated work during generation. This one is sneakier. When the model writes token 500, a naive implementation re-runs the whole prefix of 499 tokens through every layer just to append one token. Nothing about those 499 tokens changed. We are paying again for an answer we already had.

These are genuinely different. Cost one is about the shape of attention and is attacked with sliding windows, sparsity, and linear attention. Cost two is about redundancy and is attacked with the KV cache. Move the slider and watch how fast the first one runs away from you.

2. The KV cache

Save the past keys and values, then pay the memory bill.

Start with cost two, because the fix is almost embarrassingly simple. During generation, every past token has already produced a key vector and a value vector in every attention layer. Those vectors depend only on that token and the tokens before it - and none of that changes when we append something new at the end. So do not recompute them. Keep them.

That store is the KV cache. On each new step the model computes the query, key, and value for exactly one new token, appends the new key and value to the cache, and then scores the new query against every cached key. Same attention math, same answer, a fraction of the work.

Notice what is not cached: the query. A query is only ever used for the step that created it. Once token 12 has done its lookup, its query has no further job. Keys and values, by contrast, get read again on every future step, which is exactly why they are the ones worth keeping.

The work shape, in symbols

This is a deliberately simple count: one unit means processing one token's stream for one generation step. It is enough to see the shape of the win.

$$\text{without cache} = \sum_{t=1}^{n} t = \frac{n(n+1)}{2} \qquad \text{with cache} \approx n$$
  • \(n\): how many new tokens we generate.
  • \(\frac{n(n+1)}{2}\): the triangle of repeated prefix work.
  • \(n\): the line you get when each step adds only the new token.

The bill arrives as memory

Here is the catch, and it is the reason the next three sections exist. We did not make the work disappear; we traded compute for memory. Every cached key and value has to live in GPU memory for the entire generation, and the cache grows with every single token.

The size is easy to count exactly. For each layer we store one key vector and one value vector per key/value head per token. So:

Cache size, in symbols

$$\text{bytes per token} = 2 \times L \times H_{kv} \times d_{head} \times b$$
  • \(2\): one key vector plus one value vector.
  • \(L\): number of Transformer layers.
  • \(H_{kv}\): number of key/value heads (not query heads - that distinction is the whole point of the next section).
  • \(d_{head}\): dimensions per head.
  • \(b\): bytes per number, usually 2 for the half-precision formats models are served in.

Multiply by the sequence length for one conversation, then by the number of conversations you are serving at once. That last multiplication is what makes cache size a business problem.

Exercise: size the cache for GPT-2 small

GPT-2 small has 12 layers, 12 heads, a head dimension of 64, and a context of 1,024 tokens. Served at 2 bytes per number, how big is a full KV cache for one conversation? Work it out before you peek.

Answer: 2 x 12 x 12 x 64 x 2 = 36,864 bytes per token, which is 36 KiB. Over the full 1,024-token context that is about 36 MiB. Comfortable. Now redo it for a modern model with 80 layers and a 128,000-token context and you will see why people care so much about the next section.

3. Sharing keys and values

If the cache is too big, store fewer copies of it.

Look back at the cache formula and ask which term is easiest to attack. Layers are fixed by the architecture. Sequence length is chosen by the user. Head dimension changes what the model can represent. That leaves \(H_{kv}\), the number of key/value heads - and it turns out we were being wasteful there.

In classic multi-head attention, each of the (say) 32 heads owns its own keys and values. Thirty-two heads, thirty-two key sets, thirty-two value sets. But do all thirty-two really need their own? Somebody asked, and the answer was mostly no.

Multi-query attention takes the extreme position: all query heads share a single set of keys and values. The cache shrinks by a factor of 32, which is enormous - but quality drops a little, because the heads lose some independence. Grouped-query attention is the compromise that stuck: split the query heads into groups, and let each group share one key/value set. Llama 2 and Llama 3 use it, and so does nearly everything since.

Crucially, none of this changes the attention math. Every query head still computes its own scores and its own weighted blend. It just reads keys and values that a few of its neighbours are reading too. Drag the group count below and watch the same 32 query heads collapse onto fewer and fewer shared key/value sets.

Multi-head latent attention: compress instead of share

DeepSeek took a different route. Instead of having heads share keys and values, multi-head latent attention (MLA) squeezes the keys and values down into a smaller latent vector, stores that in the cache, and projects it back up to full size when it is needed. You pay one extra matrix multiply per step and save a lot of memory.

The interesting wrinkle is quality. In the DeepSeek-V2 ablations, grouped-query attention came out slightly worse than plain multi-head attention, while MLA came out slightly better - so DeepSeek got a smaller cache and a better model at the same time. That is why V3, Kimi K2, and Mistral 3 Large all build on it. It is more work to implement, which is the honest reason most teams still reach for grouped-query first.

4. Looking at less

Does token 90,000 really need to look at token 3?

Now back to cost one, the quadratic pair count. The most direct way to shrink a matrix is to stop filling in most of it. Sliding window attention does exactly that: instead of letting each token see every earlier token, it sees only the last \(w\) of them. The attention matrix goes from a filled triangle to a narrow diagonal band, and the cost per token stops growing with the sequence length entirely.

The obvious objection is that you have just destroyed long-range context, and it is a fair objection. Two things rescue it. First, information still travels further than the window, because every layer moves it another \(w\) tokens along - stack enough layers and the effective reach multiplies. Second, and more practically, models interleave: Gemma 3 uses five sliding-window layers for every one full-attention layer, so most layers are cheap and a few can still see everything. Gemma 3 also shrank its window from 4,096 to 1,024 and reported almost no change in output perplexity.

5. FlashAttention

Same answer, far fewer trips to slow memory.

This one is my favourite, because it changes nothing about the mathematics and still delivers one of the biggest speedups in the whole list.

Here is the problem it solves. A naive implementation computes the entire \(n \times n\) score matrix, writes it to the GPU's main memory, reads it back to apply softmax, writes it again, reads it once more to multiply by the values. For a long sequence that matrix is enormous, and a GPU's main memory is dramatically slower than the small scratchpad memory sitting next to the compute units. The arithmetic was never the bottleneck. The commuting was.

FlashAttention never builds the full matrix. It walks through the keys and values in tiles small enough to fit in fast memory, and it keeps a running softmax as it goes: a running maximum, a running sum of exponentials, and a running weighted output. When a new tile arrives with a bigger maximum, the partial result computed so far is rescaled to match. At the end, the answer is bit-for-bit what the naive version would have produced.

That rescaling trick is the clever part, and it is worth seeing once. Step through the tiles below and watch the running numbers correct themselves.

6. Mixture of experts

Grow the model without growing the work per token.

Every trick so far attacked attention. This one attacks the other half of the block - the feed-forward network that Chapter 5 described as "refining each token on its own." In a large model that feed-forward network holds most of the parameters, and every token runs through all of it.

Mixture of experts replaces that one feed-forward network with many of them, called experts, plus a small router that looks at each token and picks the best few. If there are 256 experts and the router picks 8, then 97% of those parameters sit idle for this particular token. The model has enormous capacity to store knowledge, but the cost of processing any one token stays small.

This is why modern model cards quote two numbers. DeepSeek V3 has 671 billion total parameters but only about 37 billion active per token. When you see a headline parameter count now, the first question to ask is: total or active?

Some designs also keep one shared expert that every token uses, on the theory that common patterns should not have to be relearned by every specialist. DeepSeek does; Qwen3 tried it and dropped it. The field genuinely has not settled this one.

7. Linear attention

What if the cache stopped growing at all?

Everything so far kept the softmax and shrank something around it. The last idea on our list is more radical: change the attention formula so the cache becomes a fixed size, no matter how long the sequence gets.

The trick hinges on a detail of the softmax. Because the exponential is applied after the query meets the key, every query is welded to every key and you are stuck computing all the pairs. Linear attention replaces that exponential with a simple positive function applied to the query and the key separately, before they meet. Once the nonlinearity is separable, the multiplication can be re-associated:

Re-associating the product

$$\text{softmax}\!\left(\tfrac{QK^{\top}}{\sqrt{d}}\right)V \quad\longrightarrow\quad \phi(Q)\big(\phi(K)^{\top}V\big)$$
  • \(\phi\): a feature map that makes the numbers positive; the classic choice is \(\text{elu}(x)+1\).
  • Left form: you must build the \(n \times n\) matrix \(QK^{\top}\) first.
  • Right form: \(\phi(K)^{\top}V\) is a \(d \times d\) matrix that does not depend on \(n\) at all. It can be accumulated token by token and kept as a fixed-size state.

That fixed-size state is the payoff: instead of a KV cache that grows forever, you carry one small matrix that gets updated as you go. Cost per token becomes constant.

So why is not everything built this way? Because a fixed-size state has fixed capacity. New associations get added into the same matrix, so once you exceed what it can hold, older memories start interfering with newer ones. Exact recall of something specific from far back - the kind of thing full attention is uniquely good at - degrades.

The 2025-2026 response has been hybrids. Gated DeltaNet, used by Qwen3-Next, adds a rule for actively overwriting stale entries rather than just piling new ones on top. Kimi Linear refines that further and pairs it with full multi-head latent attention layers in a 3:1 ratio, so three cheap layers are followed by one that can still look anywhere.

An honest caveat, because this is live research and not a settled ladder: the MiniMax team shipped M1 with linear attention and then went back to full attention for M2, reporting that the linear variant held up on ordinary prompts but struggled on reasoning and multi-turn agent tasks. Newer is not automatically better. Whether the fixed-size state is enough clearly depends on what you are asking the model to do.

Exercise: match the pressure to the fix

For each complaint, name the technique from this chapter that addresses it most directly. (1) "Our GPUs spend most of their time waiting on memory reads, not doing arithmetic." (2) "We can serve only four users at once before we run out of VRAM for their caches." (3) "We want a smarter model but our per-token latency budget is fixed." (4) "Prompts of 200,000 tokens take forever just to read." (5) "Generating token 900 seems to redo the work for tokens 1 through 899."

Answer: (1) FlashAttention, which is about memory traffic rather than arithmetic. (2) Grouped-query or multi-head latent attention, which shrink the per-token cache. (3) Mixture of experts, which grows total parameters without growing active ones. (4) Sliding-window or sparse attention, which trims the quadratic pair count during the prefill. (5) The KV cache, which is exactly the redundancy fix.

9. Going deeper

Further reading.

If you read only one thing after this chapter, make it Sebastian Raschka's architecture comparison. It is the single best running survey of what production models actually do, and much of this chapter is my attempt to walk you slowly through the pressures it catalogues.

  • Sebastian Raschka, The Big LLM Architecture Comparison A continuously updated side-by-side of modern open-weight architectures, from DeepSeek V3 through Gemma, Qwen, Kimi, and beyond. The figures are excellent.
  • Ainslie et al., GQA: Training Generalized Multi-Query Transformer Models The paper that made grouped-query attention the default, including the quality ablations against multi-head and multi-query.
  • Dao et al., FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness The original tiled-softmax paper. The word "exact" in the title is the whole point.
  • DeepSeek-AI, DeepSeek-V2 Where multi-head latent attention was introduced, with the ablation showing it beating both multi-head and grouped-query attention.
  • Katharopoulos et al., Transformers are RNNs: Fast Autoregressive Transformers with Linear Attention The clearest derivation of the re-association trick behind linear attention and its fixed-size state.
  • Moonshot AI, Kimi Linear A current attempt to make linear attention work at scale, using channel-wise gating and a 3:1 hybrid with full attention layers.
  • Beltagy et al., Longformer: The Long-Document Transformer Where sliding-window attention was worked out carefully, including how stacked layers extend the effective receptive field.
  • Shazeer, Fast Transformer Decoding: One Write-Head is All You Need Multi-query attention, the key/value sharing idea that grouped-query attention later softened into a compromise.
  • Child et al., Generating Long Sequences with Sparse Transformers The sparse attention patterns GPT-3 interleaved with full attention layers.
  • Fedus, Zoph, and Shazeer, Switch Transformers A clear route into sparse mixture-of-experts and the total-versus-active parameter distinction.
  • Jiang et al., Mixtral of Experts A modern open-weight sparse MoE model, useful for seeing real expert counts and routing choices.
  • Zhang & Sennrich, Root Mean Square Layer Normalization RMSNorm, the cheaper normalization layer that replaced LayerNorm in nearly every modern block.
  • Shazeer, GLU Variants Improve Transformer Where SwiGLU comes from, the feed-forward activation used by Llama, Gemma, and Qwen.
  • Leviathan, Kalman, and Matias, Fast Inference via Speculative Decoding A draft model proposes several tokens and the large model verifies them in parallel, cutting latency without changing the output distribution.
  • Jurafsky & Martin, Speech and Language Processing, Chapter 8: Transformers Section 8.8, "Dealing with Scale," covers scaling laws and the KV cache with the same worked-example spirit as this course.
