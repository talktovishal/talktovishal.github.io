Learning by doing

Transformers: how ChatGPT looks back at words :-).

The Transformer from first principles: let's build the attention machinery that lets an LLM use context.

I type a question into ChatGPT, and a few seconds later it writes back like it has kept track of the whole conversation. How does that happen? How does the word it know what it refers to? How does the model remember something I wrote many words ago? Let's build the core idea ourselves.

Here is the picture I want you to keep in your head. Older models often felt like a line of people whispering a message forward: each word passes a small note to the next word, and we hope the important clue survives until the end. The Transformer changes the game. It lets each token look back directly at the other tokens and ask, "which of you matters for me right now?" That move is called attention. It sounds fancy, but by the end of this chapter it will feel like a very careful weighted lookup.

This chapter is now grounded in Jurafsky and Martin's Speech and Language Processing Transformer lecture, with Hands-On Large Language Models kept as a visual companion. I am using the lecture as the coverage map, but we will rebuild the machinery with our own examples until query, key, value, residual stream, and KV cache feel like working parts.

Guiding question to keep in your pocket: when the model reads Sarah fed the cat because it and has to figure out what it means, how does it decide that it points at the cat and not at Sarah? Attention is the answer. Woohoo, this is the mechanism we are going to take apart :-)

1. One token at a time

Print one token, attach it, and ask again.

Let me clear up the first big misconception. When an LLM writes a paragraph, it does not print the whole paragraph in one shot. It predicts one token, attaches that token to the end of the prompt, and then asks the same question again: "given everything so far, what token should come next?" Predict, append, repeat. That is the whole loop.

Each trip through the neural network has a name: a forward pass. That just means the input flows through the model, the model does its calculations, and one next-token prediction comes out. So when we say "the model wrote an email," what really happened is many forward passes, each one adding one token to the growing text.

There is a word for a model that feeds its own output back in as input to make the next prediction: it is called autoregressive. (That is the same word that explains why a chatbot streams its answer to you piece by piece instead of all at once: it is genuinely making the next piece only after it has committed to the last.) Now let's do the tiny version. Press the button below and watch the prompt grow by one token per pass.

2. The forward pass

Text goes in; next-token scores come out.

So what actually happens inside one forward pass? I like to split the model into three big pieces. First comes the tokenizer (your friend from Chapter 3). It breaks the text into tokens and hands each one an integer ID. Each ID then looks up a row of numbers, its embedding, in a big table the model learned during training.

Those embedding vectors flow through the second part: a tall stack of Transformer blocks, often dozens of them, each one refining the representation a little more. Think of this stack as the model's working area. This is where it mixes context, applies learned patterns, and slowly turns plain token vectors into useful next-token evidence.

At the very top sits the third part, the language modeling head (or "LM head"). It is a single layer that turns the stack's output into one number for every token in the vocabulary, tens of thousands of them, and softmax turns those numbers into a probability for each possible next token. That probability bar chart is the model's answer. It is the very same kind of picture you built back in Chapter 1.

How to read a real model printout

The source chapter prints a small modern causal model and asks you to notice the same three-part shape. The names look intimidating, but do not let them scare you. We are just looking for the familiar landmarks: embeddings at the bottom, repeated decoder blocks in the middle, and an LM head at the top.

embed_tokens 32,064 token IDs, each mapped to a 3,072-number vector.
layers 32 repeated Transformer decoder blocks.
qkv_proj One projection that makes query, key, and value vectors for attention.
lm_head Turns a 3,072-number final vector into 32,064 next-token scores.

The LM head, in symbols

Everything above the last token's stream eventually has to become one score for every token in the vocabulary. The LM head does that with a linear projection called an unembedding, then softmax turns those scores into probabilities:

$$u = h_N^L U \qquad y = \operatorname{softmax}(u)$$
  • \(h_N^L\): the final vector for the last input token after layer \(L\).
  • \(U\): the unembedding matrix, often tied to the token embedding matrix.
  • \(u\): the logit vector, one raw score per vocabulary token.
  • \(y\): the probability distribution the decoder will choose from.

The real browser model later in this chapter exposes exactly this final \(y\): a ranked list of next-token probabilities from a genuine LM head.

3. Choosing the next token

The model gives chances; we still have to choose.

The LM head hands us a probability for every token, but we still have to pick one token to actually print. This is the same question from Chapter 1: after we have all the bars, do we always choose the tallest bar, or do we let the smaller bars have a chance too? The rule we use is called the decoding strategy.

The simplest rule is greedy decoding: always take the single highest-probability token. It sounds ideal, but it tends to produce flat, repetitive text. A livelier approach is to sample: roll a weighted die so that a token with 40% probability gets picked about 40% of the time, while less likely tokens still get an occasional turn.

The lecture gives three practical ways to keep sampling from wandering too far into the long tail. Temperature sharpens or flattens the whole distribution. Top-k keeps only the \(k\) most likely tokens, then samples from those. Nucleus, or top-p, keeps the smallest set of tokens whose probability mass reaches \(p\). Same model, same logits, different rule for choosing.

4. Parallel streams and context

Every token gets its own little track.

Here is one reason Transformers became such a big deal. The old line-of-people picture processes words one after another. A Transformer gives each token its own little stream of computation, and many streams can run at the same time. Modern GPUs love that. It is like opening many checkout lanes instead of making every customer wait in one line.

The number of streams a model can run at once is its context length. A model with a 4,000-token context has room for 4,000 streams; ask for more and it simply has nowhere to put them. This is why "context window" is a number you hear quoted for every model. It is the size of the reading space the model has available at once.

One subtlety worth pausing on: to predict the next token, the model only uses the output of the last stream. So why bother computing all the others? Because attention in that last stream reaches back and reads the earlier streams. Their work is not wasted. It is the evidence the final token leans on.

Exercise: count the streams

A prompt has 6 tokens and the model's context length is 10 tokens. How many token streams run during the forward pass, and which stream feeds the LM head for the next-token prediction?

Answer: 6 streams run, one per input token. The last stream is the one whose final vector feeds the LM head, but attention lets that last stream pull useful information from the earlier five.

5. Attention intuition

Attention is a weighted lookup.

Before we name query, key, and value, let us do the primitive version. A token is trying to update its own stream. It looks back at the tokens it is allowed to see, gives each one a weight, and takes a weighted average of their vectors. That is attention in its barest form.

The weights are the important part. If the current token is it, and cat is the earlier word that best explains it, then cat should get a large weight. If fed is not useful for that question, it should get a small one. Softmax turns all those relevance scores into weights that add to 1, so the output is a real blend, not a loose pile of numbers.

This simplified version is not yet the real Transformer equation, but it is the right mental picture. Attention mixes information across token streams. The next section adds the real roles: a query for the token asking the question, keys for the tokens being searched, and values for the information that gets copied into the answer.

A tiny weighted sum

Suppose it is allowed to read three earlier vectors, and the relevance weights after softmax are 10%, 70%, and 20%. The output is not one winner copied whole. It is a weighted mixture:

a_it = 0.10 * value_Sarah + 0.70 * value_cat + 0.20 * value_sentence the 0.70 term dominates, so the new "it" vector carries mostly cat information

The real attention head computes those weights from learned vectors instead of choosing them by hand.

The primitive attention equation

The simplified lecture version writes attention as a weighted sum over the visible context. Every \(\alpha_{ij}\) is a weight for how much token \(j\) contributes to token \(i\)'s new vector:

$$a_i = \sum_{j \le i} \alpha_{ij} x_j \qquad \alpha_{ij} = \operatorname{softmax}(\operatorname{score}(x_i, x_j))$$
  • \(x_j\): the vector currently sitting in token \(j\)'s stream.
  • \(a_i\): the attention output for token \(i\).
  • \(\alpha_{ij}\): token \(j\)'s share of the blend for token \(i\).
  • \(j \le i\): in a causal model, token \(i\) can see itself and the past.

We left one thing deliberately vague: where does \(\operatorname{score}(x_i, x_j)\) come from? That is exactly what query, key, and value vectors answer next - they are how the model computes these weights from the tokens themselves, instead of us hand-picking them.

6. Query, key, value

Ask a question, find the matching keys, and blend the answers.

Now the heart of the whole thing. Suppose the current token is it. It is basically asking, "what thing in the sentence am I standing in for?" Attention turns that question into three little vectors for every token, and gives each one a job:

  • Query: the question the current token is asking.
  • Key: the label each token holds up, "here is what I can help with."
  • Value: the information that token will hand over if it is useful.

Before we use them, though, I owe you an answer to the question I would be asking right now: where do those three vectors come from? Because it sounds like each token arrives carrying three separate things, and it does not.

One vector in, three vectors out

Each token arrives with exactly one vector: the embedding from Chapter 2, possibly already updated by earlier blocks. Call it x. The query, key, and value are all made from that same x, by multiplying it with three different matrices that the model learned during training:

q = x · WQ ← turn x into "what am I looking for?" k = x · WK ← turn x into "what can I offer?" v = x · WV ← turn x into "what do I hand over?"

This is the bit that took me embarrassingly long to internalise, so let me say it as plainly as I can. The three roles are not three properties of the token. They are three questions we ask of the same vector. The word cat does not have a key; it produces one when WK is applied to it. Change WK and the very same word offers a different label to the sentence.

And those three matrices are ordinary learned weights, exactly like the ones you trained by hand in Chapter 4. They start as small random numbers and get nudged by gradient descent until the queries and keys that should match actually do. Nobody told the model that pronouns should look for animate nouns. That fell out of predicting the next token, over and over, across a very large amount of text.

Let's actually do one projection

Talk is cheap, so here is the arithmetic for a single vector. Suppose the embedding arriving for it is these four numbers:

x_it = [ 0.2, 0.1, 0.5, 0.9 ]

And here is the query matrix. Read it as: row i says how much input channel i contributes to each output channel. Every one of these sixteen numbers would be learned during training; I picked round ones so the multiplication stays readable.

WQ, four inputs across, four outputs down
from x→ q₁→ q₂→ q₃→ q₄
x₁ = 0.20.00.00.50.5
x₂ = 0.11.00.00.00.0
x₃ = 0.50.00.00.40.7
x₄ = 0.90.00.00.01.5

Each output number is a dot product of x with one column. Four columns, four little sums:

q₁ = 0.2(0.0) + 0.1(1.0) + 0.5(0.0) + 0.9(0.0) = 0.1 q₂ = 0.2(0.0) + 0.1(0.0) + 0.5(0.0) + 0.9(0.0) = 0.0 q₃ = 0.2(0.5) + 0.1(0.0) + 0.5(0.4) + 0.9(0.0) = 0.10 + 0.20 = 0.3 q₄ = 0.2(0.5) + 0.1(0.0) + 0.5(0.7) + 0.9(1.5) = 0.10 + 0.35 + 1.35 = 1.8 q_it = [ 0.1, 0.0, 0.3, 1.8 ]

That last line is the query vector every demo on this page uses for it - notice how heavily it leans on the fourth channel, the one I am calling animate. Its key and its value come from the very same x_it, just through WK and WV instead. To keep the arithmetic on this page readable I set the remaining query, key, and value vectors by hand rather than writing out three more matrices; a real head does nothing but this multiplication, at every position, in every layer.

Quick check: a token's query and its key look nothing alike. How is that possible if both come from the same embedding?

Now the two steps

With those in hand, attention runs in exactly two steps. Step one, relevance scoring: take the current token's query and compare it against every token's key with a dot product. A big dot product means "these two match." We divide by √d to keep the numbers tame, then run the scores through softmax so they become weights that add up to 1. Step two, combining information: multiply each token's value by its weight and add them all up. Tokens that scored high contribute most. The sum is the token's new, context-aware representation. In one line: attention(q) = softmax(q · K / √d) · V.

Below is our running sentence, Sarah fed the cat because it, with hand-picked query/key/value vectors so the mechanism is visible (in a real model these are learned). The default query is it. Watch where it looks. My bet is that you will see the idea click as soon as the cat bar jumps ahead.

Why "it" finds "cat", by hand

The query for it leans hard on the "animate / living-thing" channel, because a pronoun like it is hunting for a thing it could stand in for. The key for cat leans on that same channel. So their dot product is large. The key for fed is more verb-like, so it does not match the question very well.

q_it · k_cat = high → "it" and "cat" match strongly q_it · k_the = medium → a determiner, mildly relevant q_it · k_fed = ~0 → a verb, nothing to offer "it" softmax of all six scores → cat wins most of the weight output_it = weighted sum of values ≈ mostly cat's value

The bars below run this exact calculation for every token. Because cat wins the weight, it's new vector is mostly made of cat, so the model has resolved the pronoun.

The real attention head, in symbols

The real Transformer does not compare raw token vectors directly. It first projects each stream into three roles, then scores the current query against the visible keys and blends the values:

$$q_i = x_i W_Q \qquad k_j = x_j W_K \qquad v_j = x_j W_V$$ $$\operatorname{score}(i,j) = \frac{q_i k_j^\top}{\sqrt{d_k}} \qquad \alpha_{ij} = \operatorname{softmax}(\operatorname{score}(i,j))$$ $$\operatorname{head}_i = \sum_{j \le i} \alpha_{ij} v_j \qquad a_i = \operatorname{head}_i W_O$$
  • \(W_Q,W_K,W_V\): learned matrices that create query, key, and value vectors.
  • \(d_k\): the query/key width; dividing by \(\sqrt{d_k}\) keeps scores tame.
  • \(\alpha_{ij}\): attention weight from query token \(i\) to key token \(j\).
  • \(W_O\): the output projection that returns the head to the model width.

    Why divide by √d?

    Step 4 of that walkthrough probably felt like the arbitrary one. We divided every score by √d and I said it "keeps the numbers tame," which is the kind of hand-wave I promised not to do. So here is the real reason, and it is worth understanding because it explains a failure mode.

    A dot product adds up d separate products. Add more terms and the sum naturally drifts further from zero - roughly in proportion to √d. Our toy uses d = 4, so scores land around 1 or 2. A real head uses d = 64 or 128, where the same vectors would produce scores in the tens.

    Now recall what softmax does with big gaps: it exponentiates. A score of 13 against a score of 2 is not "somewhat more attention," it is e11 times more - about sixty thousand to one. The distribution collapses onto a single token, the other weights become indistinguishable from zero, and during training the gradients through those near-zero weights vanish with them. The model stops being able to learn from anything except its current favourite.

    Dividing by √d cancels exactly that growth, so the spread of scores stays roughly the same no matter how wide the head is. Drag the width below and watch the unscaled row collapse while the scaled row holds steady.

    The mask, and why it makes GPT a generator

    Toggle the causal mask above and watch the top-right half of the grid go dark. A model that writes left to right is not allowed to peek at the future. When it is processing a token, the tokens that come after it do not exist yet. So each token may only attend to itself and the tokens before it, and the remaining weights are renormalized so each row still adds to 100%.

    This one rule is what makes a model a next-token predictor (like GPT) rather than a fill-in-the-blank reader (like BERT, whose B is for "bidirectional" precisely because it looks both ways).

    The trick under the hood is tidy: future positions get a score of -∞ before softmax. Since e-∞ is zero, those cells receive exactly no weight, and softmax shares the probability out over the allowed past. In plain English: cover the future before the model can cheat.

    The whole attention map, in symbols

    Pack all \(N\) token streams into one matrix \(X\). One matrix multiply makes all queries, keys, and values. A second matrix multiply, \(QK^\top\), makes every query-key score in the grid at once:

    $$Q = XW_Q \qquad K = XW_K \qquad V = XW_V$$ $$A = \operatorname{softmax}\!\left(\operatorname{mask}\!\left(\frac{QK^\top}{\sqrt{d_k}}\right)\right)V$$
    • \(X\): one row per token stream, shape \([N \times d]\).
    • \(QK^\top\): the full score grid, one query row by one key column.
    • \(\operatorname{mask}\): set future positions to \(-\infty\) before softmax.
    • \(A\): the matrix of attention outputs, one row per token.

    The grid below is the softmax part of this equation made visible. Full attention is expensive because the score grid is \(N \times N\).

    8. Inside the block

    Each block mixes tokens, then refines each stream.

    Now that you have seen attention as a matrix, we can put it back inside the Transformer block. The block has two jobs. Multi-head attention is the token-mixing part: it moves information from one residual stream into another. The feed-forward network is the per-token pattern machine: it processes each stream with the same small neural network.

    The word residual stream is worth keeping. A token vector does not get thrown away at every layer. It flows upward, and each module adds a useful update into that stream. This is why very deep stacks can keep the original signal alive while adding context, facts, and intermediate features.

    Most modern decoder LLMs use the pre-norm shape: normalize the stream before attention, add the attention result back in, normalize again, then add the feed-forward result. The dimensions match all the way through, so the blocks can be stacked dozens of times.

    The feed-forward network deserves a slower look. It is usually the largest learned part of a dense Transformer block. Attention decides what other tokens to read; the FFN takes each token stream by itself and runs an expand, bend, compress move: widen the vector, apply a nonlinearity, then project it back to the model width. That bend is crucial. Without it, two linear layers would collapse into one linear layer, no matter how many times you stacked them.

    Expand Map a \(d\)-wide residual stream into a much wider hidden space.
    Bend Apply a nonlinearity such as GELU or SwiGLU so the block can model real patterns.
    Compress Project back to width \(d\), then add the update into the residual stream.
    Store patterns Many facts and concepts appear to live across FFN weights and activations, not in attention alone.

    The block equation, in symbols

    These are the same steps as the diagram. The attention update mixes token streams. The feed-forward update works position by position. The residual additions keep the stream shape fixed at \([N \times d]\), so the next block can read it.

    $$O = X + \operatorname{MultiHeadAttention}(\operatorname{LayerNorm}(X))$$ $$H = O + \operatorname{FFN}(\operatorname{LayerNorm}(O))$$ $$\operatorname{FFN}(x) = W_2\,\phi(W_1x + b_1) + b_2$$ $$\operatorname{LayerNorm}(x) = \gamma \frac{x - \mu}{\sigma} + \beta$$
    • \(X\): the matrix of all token streams entering this block.
    • \(O\): the stream after attention has added context.
    • \(H\): the block output, ready for the next layer.
    • \(\phi\): the nonlinearity. Older teaching examples often use ReLU; modern LLMs often use GELU or SwiGLU-style gates.
    • \(\mu,\sigma\): the mean and standard deviation of one token vector.
    • \(\gamma,\beta\): learned scale and shift terms for layer norm.

    9. Position information

    The model also needs to know word order.

    We have one more quiet problem to solve. Attention compares vectors, but by itself it does not know that dog bites man and man bites dog mean different things. Same tokens, totally different story! A language model needs some way to know where each token sits, or every sentence starts to look like a bag of words.

    Early Transformers added a positional embedding near the bottom of the model: token vector plus "I am position 1," "I am position 2," and so on. Modern decoder LLMs often use rotary positional embeddings, or RoPE, instead. I like to think of RoPE as putting a tiny position-dependent twist into the query and key vectors before they are compared. The dot product then asks two questions at once: do these tokens match, and are they in the right relative place?

    That timing matters. RoPE lives inside attention, right before relevance scoring, so the model can ask questions like "does this key match my query, and is it the right distance away?" It also plays more nicely with long contexts and packed training examples, where absolute position numbers alone can be a clumsy signal.

    Long context is not magic context. Even with RoPE and a large window, models can use information near the beginning or end of a prompt more reliably than information buried in the middle. Keep that limit in mind when you later design retrieval prompts or evaluate long-document systems.

    Quick check: why is position information necessary if attention already sees all the tokens?

    Exercise: spot the order problem

    Compare the cat chased the dog with the dog chased the cat. If a model kept only token identities and threw away positions, what crucial fact would it lose?

    Answer: it would lose who did the chasing and who got chased. Attention needs position information so the same tokens in a different order produce different representations.

    10. Multi-head attention

    Use several attention heads, because one question is not enough.

    One attention pattern is not enough. A sentence has many kinds of relationship at once: a pronoun and its referent, a verb and its subject, a word and the punctuation nearby. So a Transformer runs attention several times in parallel, and each copy is called an attention head. Each head gets its own learned query/key/value projections, so each one learns to care about a different kind of pattern.

    A common shorthand is "split, attend, combine," but do not picture fixed chunks of the original vector being handed to fixed heads. Each head has its own learned projection matrices. It reads the full residual stream and maps it into a smaller query/key/value space for that head. The head outputs are then stitched back together. It is like asking several friends to read the same sentence, each with a different highlighter. One marks pronouns, one marks previous words, one marks subjects, and together they give you a richer picture.

    Pick a query token below and compare three heads we hand-designed. One chases meaning (the coreference head that sends it to cat), one is a "look at the token just before me" head, and one always anchors on the sentence's subject. Same words, three different stories.

    Several heads, then one projection

    Multi-head attention repeats the same attention calculation with different learned projections. Each head can learn a different relationship, then the head outputs are concatenated and projected back to the model width:

    $$\operatorname{head}_c = \operatorname{Attention}(XW_Q^c, XW_K^c, XW_V^c)$$ $$\operatorname{MultiHeadAttention}(X) = [\operatorname{head}_1;\operatorname{head}_2;\ldots;\operatorname{head}_A]W_O$$
    • \(c\): one attention head.
    • \(A\): the number of heads running in parallel.
    • \([\ldots]\): concatenate the head outputs side by side.
    • \(W_O\): the projection that folds the combined heads back into one stream.

    12. What we left out

    Everything here is correct. Almost none of it is affordable.

    Take a moment, because you have just built the actual mechanism behind every large language model in use today. The attention operation you worked out by hand - query dot key, scale, softmax, blend the values - is unchanged in a 2026 trillion-parameter model. That is not a simplification I am making for teaching. It is genuinely the same operation.

    But I have been quietly hiding a bill from you. Our sentence had six tokens. A real prompt might have a hundred thousand, and every token scores against every token before it, so the number of scores grows with the square of the length. Worse, the generation loop from the very first section re-runs the whole prefix through every layer just to add one token to the end.

    None of that changes what attention is. It changes what it costs. So that is the entire subject of the next chapter: the KV cache, grouped-query and latent attention, sliding windows, FlashAttention, mixture of experts, and the linear-attention experiments that are still being argued about right now. Every one of them is an answer to a cost you can now feel.

    One honest note before you go. The heads you designed here had tidy jobs, because I chose their numbers. Real heads are messier and mostly uninterpretable - though not always. Researchers have found induction heads: attention circuits that spot a repeated pattern like A B ... A and push B up as the next token. That is one concrete clue for how a model can appear to learn from your prompt during a single forward pass, without a single weight changing.
